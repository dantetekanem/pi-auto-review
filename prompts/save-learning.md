Save what this review learned about the codebase so the next review starts ahead. Only the coordinator calls `agentic_code_review_save_learning`, after the assessment has finished, using the original session/run IDs and a repository listed in the final review's `codebases` entries (`repository`, absolute `root`, `revision`).

Each note has a topic, a `current` block and a `delta`. The `current` block is the consolidated text the next coordinator reads first: start from the block `agentic_code_review_read_learning` returned at intake, fold in what this run revalidated, corrected, refuted or added, drop what the current revision made false, and keep it under 6000 characters. The `delta` is this run's own contribution with map source IDs; it is appended to the topic history with the run and revision and never rewritten. Omit `current` only when this run learned nothing that changes the block.

Supply `structure`, `design` and `framework`, plus `decisions` and `methods` whenever the run settled or refuted a question or learned something about how to review this codebase, and `testing` or `pitfalls` when the run produced evidence for them. Fixed line shapes keep the two review-memory topics scannable:

- `decisions`: one line per settled question: `path or symbol — claim — settled by (author reply, test, source read, thread) — run and revision — outcome (accepted, refuted, fixed, open)`. A later review re-raises a settled claim only when the cited code changed.
- `methods`: per component or area: which evidence source settled questions fastest, which lenses produced confirmed findings here, what wasted time and how to avoid it, and how long each stage took.

For monorepos, keep one repository identity/root and organize notes by repository-relative component paths, including packages, applications and Rails engines. Keep a compact, evidence-backed component index in `structure`; distinguish repository-wide facts from component-scoped sections. Record host/engine and cross-component contracts without generalizing one component's conventions to its siblings. Save navigation anchors and reusable lessons, not raw traces; link map evidence and mark unexamined components. Include only observed or revalidated facts and scope unknowns explicitly. This tool validates storage and record shape, not the truth of a claim.

Notes are private Markdown files under `auto-review/codebases/<actual-root-folder>/`. The current block is replaced; history entries keep their run, revision and evidence links. Identical retries preserve bytes; conflicting retries and repository-name collisions fail without replacing prior notes. Updates are serialized, locked between processes and atomic per file, not a transaction across all topics. On partial failure retain the per-run evidence and report the gap; an identical retry can finish missing files. Never remove another writer's lock or use direct edits as a fallback.
