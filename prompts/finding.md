Submit one durable, structured review finding for an existing prepared run.

Use `agentic_code_review_append_finding` only with the supplied session and run IDs. Submit evidence collected by inspecting the code and its contracts. Do not read or edit the shared review artifacts to submit a finding; this tool owns that update.

Write `title` and `humanReadable` under the supplied `voice.md`: the title is a short sentence naming what goes wrong, and `humanReadable` (at most 400 characters) is what you would say to the author at their desk, leading with what they would see go wrong, then what you would do or ask. New runs require `humanReadable` and a one-letter `rating`: A safest, B minor improvements, C bounded concern, D blocker or material missing proof, E confirmed serious failure, F confirmed critical failure. Keep uncertainty and origin explicit; a rating is not proof or an automatic blocker. Old runs may omit both fields. The tool records actual model/thinking metadata from the executing context; do not supply attribution yourself.

Classify confirmed defects as `bug`; they require expected and actual behavior, origin, blocking status, verification, and concrete evidence. Use `question` for something the author can answer that changes the assessment and the review could not settle: `humanReadable` is the question as you would ask it, `impact` is what changes with the answer, `suggestedFix` is what would settle it. Use `fix` or `nit` only for nonblocking suggestions. Set `lens` to the `taste.md` lens that produced the lead; for a bug, the observation that surfaced it. The tool validates record shape and persistence only; it does not prove the finding semantically.
